# FRC Robot Vision

FRC vision with pretrained Ultralytics YOLO26, ROCm training, and offline match-video review. The current trained checkpoint is single-class (`frc_robot`); inference is ready to consume a future four-class model. Detection is isolated in `src/frcvision/video.py`; tracking, OCR, and field projection are separate post-processing modules.

## Multiclass detector roadmap

The target YOLO label map is:

| ID | Class | Pipeline use |
|---:|---|---|
| 0 | `game_piece` | Draw and count piece detections; keep out of robot tracking and field projection |
| 1 | `red_robot` | Track, smooth, project to the field map, and optionally read the bumper number |
| 2 | `blue_robot` | Track, smooth, project to the field map, and optionally read the bumper number |
| 3 | `OCR_region` | Mark a robot-number crop; RapidOCR decodes the digits asynchronously |

Inference reads class names from the selected checkpoint, renders auxiliary classes, and reserves tracking/map positions for robot classes. The optional OCR stage can use an `OCR_region` crop associated with a robot, with a lower-robot crop as fallback. The current public training source labels robots only and the configured downloader deliberately maps them to `frc_robot`; therefore the checked-in `config/train.yaml` and existing checkpoint remain single-class. **Do not train or advertise the four-class model until the dataset YAML and labels contain all target classes.** The class-aware inference is in place, but it does not create labels or enable meaningful detection of classes absent from training. New training data should label red/blue alliance per robot, game pieces, and tight readable-number regions, then use a separate multiclass dataset YAML/checkpoint. Keep the season explicit because game-piece appearance changes by game.

## Dataset provenance

The default source is [Jerry Wu / FRC 114 robot dataset](https://universe.roboflow.com/bnenne/jerrywu_frc114_robot_v2-przxh-99ob2/dataset/1), mirrored in the public [`Bnenne/RobotDetection`](https://github.com/Bnenne/RobotDetection/tree/main/RobotDetectionLabels) repository. Its exported metadata lists 3,250 images and a single robot class; the source split contains train, validation, and test partitions. The dataset declares **CC BY-NC-SA 4.0**. It can be fetched directly from GitHub without an API key. The downloader retains the provided train/validation/test split, merges all robot labels into `frc_robot`, and records a pinned repository revision after download. This license is noncommercial and requires share-alike for adaptations; check the [license text](https://creativecommons.org/licenses/by-nc-sa/4.0/) before any deployment or redistribution.

Two optional Roboflow Universe sources remain in `config/datasets.yaml`: 2026 FRC Robots (**CC BY 4.0**) and a small FRC Robot Detection set (**MIT**). Exporting those sources requires a Roboflow API key. The default direct-GitHub source does not. Community annotations should be sampled and checked before treating validation numbers as authoritative.

Download and prepare the configured direct source:

```bash
python scripts/download_dataset.py --source frc-robot-detection-github
```

The script sparse-clones the GitHub repo at pinned revision `6e5ac58bd0ebc11e5a3697151ea6aef55885660e`, stores the source under `RoboPerception-data/datasets/raw/`, and prepares YOLO layout under `RoboPerception-data/datasets/frc_robot`. A fixed 20% validation split (seed 42) is only used when a source has no usable partitions. Images derive from video frames, so inspect source metadata for cross-split near duplicates before interpreting validation metrics.

## Environment and ROCm preflight

Use the pinned AMD gfx900 wheel set below in Python 3.12. It targets the WX 9100 explicitly; generic PyTorch ROCm wheels omitted runnable gfx900 kernels on this host.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
# Install the pinned gfx900-targeted PyTorch nightly, then the application packages.
python -m pip install --pre -r requirements-rocm-gfx900.txt
python -m pip install -r requirements.txt
python src/frcvision/device.py --device 0
```

The preflight executes and synchronizes a GPU matrix-multiplication kernel. It passes on AMD Radeon Pro WX 9100 at PyTorch `2.13.0a0+rocm7.14.0a20260612` and reports architecture `gfx900:xnack-`, PCI bus 25 (GPU 0). Training refuses to start unless the selected device passes. This host has two WX 9100s and an NVIDIA Quadro P600; use AMD index 0 to leave the other project's active AMD index 1 untouched. The training script disables legacy MIOpen assembly convolution kernels and selects FAST solver discovery; this avoids an observed illegal-memory-access failure during grouped-convolution backpropagation on gfx900. AMD documents these controls in its [MIOpen environment-variable reference](https://rocm.docs.amd.com/projects/MIOpen/en/develop/reference/env_variables.html). AMD's current [ROCm compatibility matrix](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html) omits gfx900 from standard supported-device tables, so this is a pinned gfx900 nightly build rather than a generally supported wheel. Do not upgrade the ROCm wheel set without rerunning the kernel preflight and a training smoke test.

```bash

```

Training starts from Ultralytics `yolo26n.pt`; the checked-in baseline config uses 640 px, batch 24, seed 42, 20 epochs, and patience 8. On the WX 9100 this batch uses about 6.5 GiB VRAM. Adjust batch/epochs for available time and memory. YOLO26s is available, but train and evaluate nano first; try small only if test recall is insufficient and measured latency has headroom. The evaluation script emits precision, recall, mAP50, and mAP50-95 and supports `--split val` or `--split test`. Keep each run's Ultralytics result artifacts beside the checkpoint.


`yt-dlp` downloads the public video locally and inference works offline afterward. The pipeline encodes annotated playback as H.264/yuv420p, caps output width at 960 px while preserving aspect ratio, and moves the MP4 index to the start for progressive playback. The dashboard defaults to confidence 0.50 and CPU; select AMD Radeon Pro WX 9100 GPU 0 when it is free. Raise confidence to suppress weaker boxes or lower it to retain more distant/occluded robots. On validation data, confidence 0.25 produced precision/recall 0.911/0.876 and 0.50 produced 0.937/0.841. On every tenth frame of the held-out event video, 0.50 reduced detections from 7.22 to 4.67 per sampled frame. That is a box-count change, not a false-positive rate: the event video is unlabeled. Visual review found false positives on people/field equipment and duplicate robot detections in broadcast picture-in-picture panels. A confidence threshold alone does not remove the highest-scoring broadcast-panel detections; use an event-specific region of interest or add representative broadcast negatives before relying on this model for field-only counts. Keep the URL, event/match, download date, checkpoint hash, confidence, resolution, and summary metrics in the result ledger below.

The downloader records each match's three red and three blue team numbers from its The Blue Alliance match page in a sibling .roster.json file; the lineup is cross-checked against the official FIRST match-results page. The verified lineups are also listed in config/generalization_videos.yaml. Keep downloaded, copyrighted footage in the HDD-backed data directory for local evaluation; do not add it to the source repository.

For roster-assisted OCR, the detector's bumper color selects the alliance roster. Exact team matches can confirm after repeated reads. A partial read can be corrected by one edit when at least three digits were read and the closest roster entry is unique across both alliances. Short, ambiguous, wrong-alliance, and out-of-roster reads are rejected. Two-digit fuzzy reads are intentionally rejected because they can confuse a partial number with a misread neighboring team number (for example, `18` could be `180` or a misread `16`). Raw OCR text and the saved crop remain available for review, and partial corrections record both the raw read and matched team number. Videos without a roster sidecar keep unvalidated OCR behavior.

## Local dashboard

```bash
streamlit run app.py
```

OCR is on by default and installs with `python -m pip install -r requirements.txt`. The bounded worker first isolates red/blue bumper panels inside confirmed robot boxes, then reads digits with [RapidOCR](https://github.com/RapidAI/RapidOCR)'s ONNX Runtime backend. If a read is weak or fails roster matching, it retries that crop enlarged up to 3× (1600 px long-edge limit). Strong reads avoid the extra CPU pass. It does not OCR full frames or queue work while busy. Each sampled crop, including unreadable samples, is saved at its original size beside the annotated clip and synchronized to playback; raw candidates remain unconfirmed until two matching high-confidence reads occur on the same track. The player provides a crop thumbnail, confidence, track ID, clip time, and a jump-to-sample control, and the OCR review expander lets you inspect the saved image directly. This makes false reads and unreadable crops reviewable instead of silently dropping them. The detector is still single-class and can mistake people or equipment for robots; OCR candidates on those detections must be rejected during review. Higher-resolution input materially helps: the 720p Einstein feed produced only three isolated partial Tesseract reads, while the 1080p version shows legible bumper panels such as 4272 and 8044 under RapidOCR. Low-resolution, occluded, or angled bumpers can still remain unidentified. The OCR engine uses one CPU thread asynchronously; compare end-to-end throughput against source FPS on the Xavier target before live deployment. RapidOCR code and its distributed OCR models are Apache-2.0; ONNX Runtime is MIT-licensed. No Xavier throughput result has been recorded yet.

Upload a match video or select one in the local `videos/` output folder, choose a checkpoint, set confidence and inference device, then process it. The UI plays the aspect-ratio-preserving annotated MP4 above an AdvantageScope 2025 REEFSCAPE field image, with track positions synchronized to playback and seeking. Once OCR confirms a bumper, map markers display `Team ####` instead of the temporary `T#` label; the bounding-box annotation also includes the team number and clip-local track ID. The track ID remains available in the map marker details. The image is the welded-field asset, oriented red alliance left and blue alliance right. Detections use AdvantageScope's wall-blue coordinates: x=0 is at the blue wall and +X points toward red; +Y points left of +X, toward the bottom of this image. This field artwork comes from [AdvantageScopeAssets](https://github.com/Mechanical-Advantage/AdvantageScopeAssets) and credits the [original 2025 CAD render](https://www.chiefdelphi.com/t/4k-field-image-2025-reefscape/478797); see [asset credits and license notes](assets/field-2025/ASSET-CREDITS.md). Processing uses Ultralytics [ByteTrack](https://docs.ultralytics.com/modes/track/) to keep clip-local robot IDs across frames, including brief occlusions. IDs are estimates and can switch after long occlusion or camera cuts; they are not known team identities. Bounding boxes and map positions use an exponential moving average. **Track smoothing** defaults to α=0.35; lower values smooth more but add motion lag, while 1.0 disables smoothing. **Confirm over frames** defaults to 3 sightings before displaying a new track, suppressing short hits at the cost of a brief appearance delay. **Hold through missed frames** defaults to 6 frames; those map markers fade at their last observed position and are shown separately from current detections. This short display hold is separate from ByteTrack's 30-frame lost-track buffer. Expand **Calibrate the field projection** and enter the video pixels for red-top, blue-top, blue-bottom, and red-bottom carpet corners, in that order, then save the calibration for reuse with that clip. Use a steady wide shot: camera cuts, zooms, and broadcast insets invalidate a single calibration. Full-image defaults are only approximate. Field dimensions default to the 2025 REEFSCAPE field asset size (17.548 × 8.052 m; [official FIRST 2025 game manual](https://firstfrc.blob.core.windows.net/frc2025/Manual/HTML/2025GameManual.htm)); update them for another season. Processing is offline once the video, checkpoint, and local field image are available; uploaded videos are saved in the configured data root. Each processed clip stores per-frame tracked detections, OCR decisions, saved crop evidence, and held markers. The dashboard reports current detections, average model latency, inference FPS, OCR attempts/candidates/confirmed IDs, and per-frame CSV metrics.

### 2025 Reef-base exclusion

For fixed-camera Reefscape footage, calibrate the four carpet corners in the annotated playback view and save the calibration. This saves calibration with the processed clip and source video. The field map then filters projected robot floor points inside the two physical hex Reef footprints; it does not exclude the surrounding Reef Zones. Select the same source video, ensure **Reject detections centered on the 2025 Reef bases** is enabled, and process again to remove those detections from annotated boxes, map positions, and per-frame detection counts. Filtering uses each bounding box's bottom-center and a floor-plane homography, so it requires a stable camera view; camera cuts, zooms, and picture-in-picture invalidate the calibration and can cause false filtering. Calibrate each stable view separately. Footprints are traced from the bundled AdvantageScope field art, whose dimensions and crop are recorded in `assets/field-2025/config.json`; FIRST describes each 2025 Reef as a 5 ft 5½ in hexagonal structure ([2025 Game Manual, §5.3](https://firstfrc.blob.core.windows.net/frc2025/Manual/HTML/2025GameManual.htm)). This does not suppress detections in the broader Reef Zone because robots can legally occupy that zone. For tailnet playback, expose the processed directory with `tailscale serve --set-path=/processed --bg /home/brian/Projects/RoboPerception-data/processed` and the field art with `tailscale serve --set-path=/field --bg /home/brian/RoboPerception/assets/field-2025`; set `FRC_VIDEO_BASE_URL` and `FRC_FIELD_IMAGE_URL` if the node's MagicDNS address differs from the configured defaults.
